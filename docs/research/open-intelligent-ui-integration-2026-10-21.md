# Open Intelligent UI 与 LYStar Code Web 接入方案

状态：会话内交互回答已接入 Web Runtime。第一至十二节保留研究建议，第十三节记录前期原型，第十四节记录本次正式接入、实测与限制；当前行为以第十四节和源码为准。

研究日期：2026-10-21，本机时区 UTC+8。

## 一、结论与推荐范围

**建议接入 OpenUI 的交互式回答能力，保留 LYStar Code Web 的工作台、Agent、会话、Gateway 和 Runtime，不整体引入演示应用。**

具体采用 Thesys 的 OpenUI Lang 1.0 与独立 React `Renderer`，让 Agent 在普通回答中按需生成可操作的比较表、计算器、图表和分步解释。控件与视觉继续使用 LYStar 已有组件和 token。

先完成“当前会话中的交互式结果”，验证价值与稳定性；跨设备共享控件状态、直接查询数据源、修改业务数据属于后续独立范围。第一阶段采用已有消息文本承载交互程序，不修改 Web Runtime Protocol。

建议第一批交付三个场景：

1. **方案比较**：切换筛选或权重，查看比较结果与假设；必要时把选项带回对话继续讨论。
2. **参数推演**：修改并发数、任务量等输入，观察计算结果与图表变化；公式与适用条件同时可见。
3. **已有结果分析**：对用户提供或已有工具取得的数据快照进行筛选、排序和图表展示；保留数据来源与时间。

这些场景围绕开发者的理解与决策，不将 LYStar 改造成通用地图、旅行规划或游戏平台。

## 三、这个项目真正提供了什么

### 3.1 它不是让模型直接编译 React 应用

主路径是：

```text
应用定义组件、参数、函数和动作
              │
              ▼
组件规格与语言规则提供给模型
              │
              ▼
模型输出 OpenUI Lang 程序
              │
              ▼
Parser / Evaluator 解析与计算
              │
              ▼
Renderer 使用注册的 React 组件展示
              │
              ├─ 修改 $变量 → 本地重新计算与展示
              └─ 宿主动作 → 交给应用处理
```

普通交互使用 `$变量`、表达式和 `@Set` 等动作，不必为每次点击调用模型。`HtmlView` 是另一路能力：它把 HTML/JS 放入 iframe，不能与组件语言的运行方式混为一谈。[S1][S2][S5]

### 3.2 能力与适用关系

| 能力 | 源码情况 | LYStar 采用方式 |
| --- | --- | --- |
| 组件注册与参数约束 | `createLibrary`、`defineComponent` 与 Zod schema | 采用机制，注册 LYStar 自己的组件 |
| 增量展示 | Renderer 接收程序文本和 `isStreaming` | 保留现有 WebSocket，使用收到的文本，不引入演示的 SSE 链路 |
| 交互状态 | `$变量`、`initialState`、`onStateUpdate` | 使用 SDK 状态接口，状态归属由 LYStar 负责 |
| 动作回调 | `onAction`，事件包含类型、参数和表单状态 | 接到已有发送、资源打开和复制入口 |
| 图表、表格、布局 | 演示内有自定义组件实现 | 参考 schema 与组合方式，优先复用现有 UI 和图表依赖 |
| 本地计算 | 核心表达式与演示附加函数 | 只纳入首批场景实际需要的函数，并验证数值语义 |
| Query / Mutation | Renderer 支持 `toolProvider` | 首期使用数据快照，不直接连接 Runtime 或 MCP |
| HTML/JS 页面 | `HtmlView` iframe | 首期不纳入；有明确自由页面需求时单独评估 |

SDK 1.0.0 声明文件已确认的主要接口是 `response`、`library`、`isStreaming`、`initialState`、`onStateUpdate`、`onAction`、`onError` 和 `toolProvider`。状态回调名称是 `onStateUpdate`，不是 `onStateChange`。[S5]

### 3.3 不能把演示效果直接当作接入保证

- **自有模型路径没有 Cloud 输出纠错。** 主项目支持直连 OpenAI-compatible API，使用生成的完整提示词；源码没有为这条路径实现 Cloud 的纠错能力。[S3]
- **演示存储不是 LYStar 会话存储。** 演示在浏览器 localStorage 中保存 thread 和 message，不能替代 LYStar 的历史、分支、租约与重连机制。[S4]
- **示例仪表盘不代表真实数据连接。** `demo-data.ts` 生成订单、工单和流量样例；不能把这些数据函数接成产品数据。[S7]
- **组件参数约束不证明内容正确。** 程序可以通过解析，但模型仍可能写错公式、来源、单位或解释，必须另行核对。
- **README 有滞后描述。** README 的部分段落称聊天仅浅色；当前 `page.tsx` 和线上首页已提供主题切换。方案因此以实现和实际观察为准。

| `packages/web/src/state/workbench-session-actions.ts` | `sendMessage`、prompt / follow-up / steer、发送条件与接受状态 | 交互动作复用此路径，并核对来源会话 |

| `packages/web/src/components/ai-elements/resource-preview.tsx` | 会话图片、项目资源与查看器 | 交互块图片继续走已有资源能力 |
| `packages/web-protocol/src/schemas.ts` | Transcript 类型与既有会话契约 | 首期沿用 assistant 文本；后续有明确需求才增加结构化类型 |

现有 `jsx-preview.tsx` 是基于 `react-jsx-parser` 的 JSX 预览组件，不是 OpenUI Lang Renderer；工作台也没有实际导入它。文件存在不能算交互式回答已具备接入条件。

`MessageResponse` 还用于压缩摘要、文件预览和协作消息。若把特殊代码块处理直接全局打开，会让示例文档或摘要意外变成可操作内容。因此必须由助手结果宿主明确启用。

## 五、方案比较与选择

| 路线 | 优点 | 对 LYStar 的代价 | 判断 |
| --- | --- | --- | --- |
| 整体迁入 Thesys 应用 | 接近演示外观 | 重复聊天壳层、模型入口与浏览器会话存储；要迁移 Next.js 路由 | 不推荐 |
| 独立 Renderer + LYStar 组件库 | 保留执行链路；模型能组合界面；改动集中 | 需要组件注册、生成规则、状态宿主和错误展示 | **推荐** |
| 仅借鉴界面，为每个场景写固定卡片 | 行为最确定 | 每类新回答都要开发专用组件，不能覆盖开放组合需求 | 用于真实业务操作，不替代交互回答层 |
| 整套引入 CopilotKit / LangGraph | 具备自由 HTML/JS 与 Agent 示例 | 重复现有 Agent、Runtime 和事件链路，接入面更大 | 当前不推荐 |

这里推荐 OpenUI 的理由是“回答能组合和计算”，不是“现有页面组件不够多”。业务状态、文件操作和 Git 写入继续由现有产品能力负责。

## 六、推荐架构与第一阶段实现

### 6.1 数据主线

```text
现有 Coding Agent + 已选模型
  │ 按需加载交互回答的组件规格与语言规则
  ▼
普通助手消息：文字 + 指定交互程序块
  │ 现有 Runtime → Gateway → WebSocket / Transcript
  ▼
LYStar 助手结果宿主
  ├─ 普通文字 → 现有 MessageResponse
  └─ 交互程序 → OpenUI Renderer → LYStar 注册组件
                       │
                       ├─ 本地计算 / 筛选 → 更新当前块状态
                       └─ 继续讨论 → 现有 sendMessage
```

新增的是回答的展示能力，而不是第二套会话或第二个模型代理。

### 6.2 文本承载约定

建议在助手结果中保留一个专用代码块标签，例如 `lystar-ui`。这是拟新增的 LYStar 包装约定，不是上游原生协议名称。块内是 OpenUI Lang 原文；块外保留结论、数据依据与必要说明。

采用这条路径的依据：现有 Streamdown `2.4.0` 已支持自定义 renderer，其输入包括 `code`、`isIncomplete` 和 `language`。现有消息链路可以传递程序文本，无须先增加协议类型。

接入规则：

1. 仅明确启用交互能力的助手结果识别该标签；用户消息、思考、文件正文和工具原始输出按原方式显示。
2. 普通代码块、Mermaid 与现有 Markdown 行为保持不变。
3. 流式阶段可显示逐步形成的内容，但生成中的输入与提交动作不可用。宿主同时判断流状态、原文完整性和解析结果，不能只依赖 Markdown 自动补全后的闭合标签。
4. 接收中断、原文缺失或解析失败时保留文字结论、程序原文与真实错误，不把局部可见误报成完整成功。
5. 旧 TUI 或不识别该标签的客户端仍得到普通文本代码块；不改变其执行能力。

### 6.3 完整文本与历史恢复

LYStar 存在两层长文本处理：前端展示会截断，Runtime 历史也可能通过 `contentRef` 提供全文。因此“代码块存在”不足以证明程序完整。

建议小型交互块优先保持紧凑。遇到截断消息时，先显示交互内容入口；用户打开后复用 `readTranscriptText` 读取全文，再定位、解析对应程序。禁止拿 16,384 字符预览直接恢复交互，也不为了找交互块自动读取整个历史会话。

当前阶段不承诺所有长程序在历史首屏自动展开；这能避免为少量交互内容破坏已有的按需读取方式。

### 6.4 状态归属

| 状态 | 建议归属 | 语义 |
| --- | --- | --- |
| 程序原文、原始数据与结论 | 原助手消息 / 现有 Transcript | 可恢复的回答依据 |
| 滑块、筛选、输入与勾选 | 交互块视图状态 | 用户对这份回答的本地操作，不改写原始消息 |
| 继续讨论的选项和输入 | 正常用户消息 | 发送给 Agent 的明确上下文 |
| 工具运行与业务状态 | 现有 Runtime 与工具结果 | 不由模型生成的卡片重新定义 |

推荐首期保留同一浏览器的控件状态，使用 SDK `onStateUpdate` 保存、`initialState` 恢复。存储只包含视图状态，不复制会话正文。存储键由会话、稳定消息标识、块位置和程序/组件契约版本共同确定。

视图状态必须在虚拟列表卸载前仍可访问；刷新后从浏览器存储恢复。原文改变、块被删除或契约版本不兼容时，旧状态不套到新程序上。原会话删除时清理对应状态。

生成阶段不允许用户修改控件，因此实时转历史时主要解决标识交接；不要用随 token 变化的整段文本 hash 作为 React key。最终稳定身份仍需在 PoC 中对照现有实时/历史映射确认。

此范围不含跨设备同步。若需要手机与电脑共享筛选结果，应在后续阶段增加服务端状态契约，而不是假装 localStorage 能同步。

### 6.5 动作与已有链路的关系

| 动作 | 首期处理 |
| --- | --- |
| 修改参数、切换步骤、筛选已有行 | 块内计算，不调用模型 |
| 复制结果 | 复用已有复制能力，反馈真实成功或失败 |
| 打开图片、文件 | 使用现有资源解析与查看入口 |
| 打开外部链接 | 沿用现有外链交互 |
| 继续讨论 | 展示可读的选项和输入，经现有发送动作进入同一会话 |
| 运行命令、写文件、提交 Git 或调用任意 MCP 工具 | 继续通过既有 Agent / 工具流程；交互块不新增此类直达入口 |

需要特别处理发送语义：目前 `sendMessage` 在不满足发送条件时可能直接返回，返回值本身不能证明消息已被接受。宿主必须展示已有的接受、排队或失败结果，不能在 `await sendMessage()` 后无条件显示“已发送”。

动作还必须核对交互块所属会话与当前操作上下文，防止切换会话后把旧回答中的选择发给新会话。运行中沿用现有 follow-up 规则，不暗中转成 steer。

### 6.6 数据和计算

首期 `toolProvider` 不连接真实工具。数据来自用户输入或已经取得的结果快照，交互只处理这些明确输入。

每份分析同时说明来源、取得时间、单位、公式和假设。模型推断与实测结果分开。对于要求准确的统计，先在已有工具中取得或确定计算数据，再交给界面展示，不能仅凭图表可渲染就宣称数据正确。

## 七、组件、生成规则与视觉

### 7.1 第一批组件

| 组 | 建议内容 | 责任 |
| --- | --- | --- |
| 布局与正文 | 列、行、自适应网格、标题、说明、分隔 | 组合回答结构；保持对话正文主次 |
| 输入 | 数字输入、下拉、滑块、复选、按钮 | 提供首批场景需要的交互 |
| 数据 | 比较表、柱状/折线图、结果数值 | 明确字段与单位，不猜缺失值 |
| 分步解释 | 步骤切换、简图或已有图示能力 | 展示推演顺序，不伪造 Agent 运行进度 |

不整包复制 `library.ts`。演示会同时引入地图、媒体、SVG、特效和大量函数；首批组件应由三个实际场景倒推。图表优先复用仓库已安装的 `@ant-design/plots`；是否用于具体图形，由 PoC 核对数据契约与实际加载代价。

### 7.2 生成规则

通过现有 Skill / 扩展加载能力按需向 Agent 提供语言规则、组件规格与少量中文例子；具体入口在实施前核对既有机制。不能用演示的 UI-only 系统提示替换 Coding Agent 的主提示词。

组件规格与生成规则由同一注册定义导出，避免手写两份参数顺序。包装标签、中文文案、单位和三类示例由 LYStar 维护。模型只使用实际注册的组件与函数。

初期由用户明确要求交互分析，或明确选用该能力；普通修复、简短解释和执行结果仍使用普通回答。先验证用途，再决定是否增加自动选择展示形式的逻辑。

主项目 README 提到完整提示词约 8,000 tokens，但这不是 LYStar 精简组件库的测量结果。实际新增 token、首屏时间、合法输出率与纠正成本需在小样本中记录，不能直接沿用上游宣称。[S1]

### 7.3 视觉与使用路径

- 交互内容放在对应助手结果中，保留文字结论；不新增工作台一级导航或第二个聊天窗口。
- 操作行只显示当前需要的重置、复制、继续讨论等入口；程序原文与错误详情按需查看。
- 复用 `packages/web/DESIGN.md`、现有 UI 组件、Lucide 与语义 token，不引入 OpenUI 的聊天外壳和第二套主题。
- 桌面保持正文宽度内的比较布局；窄屏改为单列，表格在局部滚动，不能让整页横向溢出。
- 浅色、深色与跟随系统沿用项目 token。控件焦点与触摸操作沿用现有规范。

以上是设计决定，不是已完成的设计图或页面验证。

## 八、依赖与许可处理

建议以已核对的 `react-lang@1.0.0`、`lang-core@1.0.0` 作为 PoC 候选，不使用浮动版本。若组件注册直接导入 Zod，应在对应包显式声明依赖；优先验证现有 `3.25.76` 的 `zod/v4` 出口，避免只为演示整体升级 Zod。

这些 SDK 的 peer 范围接受 Zod `^3.25.0 || ^4.0.0`；这只证明声明允许，不能替代 LYStar 类型检查。`@modelcontextprotocol/sdk` 是可选 peer，不因 Renderer 支持 MCP 就在浏览器中增加 MCP 客户端。[S5][S6]

`lang-core@1.0.0` 包含 postinstall 入口。依赖安装沿用仓库 `--ignore-scripts` 规则，并核对安装锁生成规则，不自动放行生命周期脚本。生成组件规格所用 CLI 仅在确有需要时作为开发依赖纳入，不进入运行链路。

主项目与核对的 SDK 包标注 MIT；引入代码时保留相应版权和许可声明，并登记实际采用的第三方内容。地图、图片检索等未纳入首期的外部服务条款不据此推定。[S8]

## 十、主要风险与验收方法

| 风险 | 实际依据 | 处理与完成依据 |
| --- | --- | --- |
| 自有模型生成无效程序 | 直连路径无 Cloud 纠错 | 精简组件库、明确例子；记录生成失败；错误时文字与原文仍可读 |
| 程序通过解析但公式或数据错误 | 类型只能约束结构 | 核对公式、单位、来源与代表性输入结果 |
| 长回复截断 | 当前 16,384 字符展示限制与 contentRef 全文机制 | 从完整原文恢复，截断内容不激活交互 |
| 滚动或切换丢失输入 | 现有虚拟列表会卸载消息 | 状态置于行外；滚出、返回、切换、刷新后检查恢复 |
| 实时转历史重建了错误实例 | 现有 live / history 各自有标识 | 生成中禁止输入；核对稳定身份交接及多块区分 |
| 点击后发错会话或假报成功 | sendMessage 使用当前会话，且可能提前返回 | 来源上下文校验；以真实接受/排队/失败状态展示结果 |
| 普通 Markdown 被意外执行 | MessageResponse 被多个区域复用 | 只在明确启用的助手结果识别专用标签 |
| 首屏加载与重渲染增加 | 新增 Parser、Renderer 和组件依赖 | 在同一会话对照接入前后数据；无真实差异时不追加复杂优化 |
| 上游变更影响已有回答 | 组件名、参数顺序与语言版本参与解释 | 固定依赖和组件契约版本；升级前回放已有程序 |

建议验收场景：

1. 修改一个输入，公式和图表按约定同时变化，过程中不调用模型。
2. 从比较结果继续讨论，Agent 收到明确的选项及输入；正常正文仍连续可读。
3. 流式半截、中止、未知组件、非法参数各显示真实状态，聊天输入与其他消息仍可用。
4. 滚出交互块再返回，状态不丢；切换会话、刷新页面后恢复到该浏览器保存的状态。
5. 重新加载历史与展开长回复，使用完整程序，并保持不同消息/块状态隔离。
6. 切换会话后，旧块动作不会发到新会话；运行中继续讨论沿用 follow-up。
7. 在 390px 与桌面宽度、浅深主题下检查关键场景；键盘可完成主要输入和操作。
8. 原有 Markdown、普通代码、Mermaid、图片、文件链接、工具详情和消息复制保持原行为。

实施后的基础检查使用 `npm run check` 与已有相关定向测试。建议补充直接覆盖新增解析与状态行为的最小单测，但必须取得 Yean 明确授权；本方案本身不视为测试编写授权。E2E、构建和真实模型请求按具体授权执行，不默认运行全量测试或大批量模型评测。

真实模型质量目前未知。若获准做模型验证，建议先对三个场景分别生成少量结果，记录合法性、计算正确性、修正次数和耗时，再决定首发支持哪些已配置模型；不承诺“任意模型都能可靠生成”。

## 十一、何时扩展 Runtime 契约

出现以下明确需求后，再评估结构化 `interactive_ui` / artifact 投影：

- 跨设备共享或协作编辑控件状态。
- 交互块需要独立版本、定位、导出或稳定引用。
- 控件需要通过已有 Runtime 能力刷新真实数据，而不只是处理快照。

届时由协议定义版本、块标识、程序/内容引用、来源和状态修订；Runtime 管理持久状态与数据调用，Gateway 做投影，Web 只展示。必须同时考虑实时事件和历史投影；不能只新增前端类型。

SDK 的 Query / Mutation 是通用工具桥，不天然拥有 LYStar 的会话语义。后续应按具体场景映射到已有命令，不能把整个 MCP 或任意工具执行入口交给生成页面。

这不是首期必经迁移。若文本块已经满足实际用途，就停在首期结构，不为了“架构完整”再建 artifact 平台。

## 十四、正式接入与验证

### 14.1 正常使用

在源码版 Web 会话中，可以直接要求“给我可改参数的推演”或“用可搜索、勾选的表格比较方案”。Runtime 已默认提供 `get_ui_spec` 与 `present_ui`，无须安装项目扩展；已有会话在恢复时同样装配。生成过程复用当前会话模型，不引入 Cloud、固定模型或预算配置。

正式链路为：

```text
当前会话模型 → get_ui_spec（同源规格）→ present_ui（校验并发布）
                                           │
                                现有工具事件 / Transcript
                                           │
                              OpenUI Renderer + LYStar 控件
                                ├─ 改参、搜索、勾选：本地处理
                                └─ 继续讨论：原会话 sendMessage
```

当前组件为 Stack、Text、StatusSummary、ResultsTable、DataTable、Continue、NumberInput、Value。DataTable 支持列与行数据、搜索和勾选；NumberInput 修改状态变量，Value 展示表达式结果。检查类组件仍可用于实际检查数据，但不限制其他回答必须先检查项目。

生成规格与组件参数来自 `web-protocol/src/interactive-ui-library.ts`，前端直接复用定义。发布前校验根节点、组件、参数、完整性、数据表引用和数值输入初始值；错误返回给原 Agent 修正。渲染错误可带回会话；原文按需查看。

视图状态包括参数、检查筛选、勾选、表格搜索和表格勾选。同一浏览器可刷新恢复；不同会话、工具调用相互隔离，程序改变时不套用旧状态；重置还原初值，删除会话清理本地状态。交互结果从工作过程中独立展示，普通工具仍沿用原折叠逻辑。

依赖固定为 `@openuidev/react-lang@1.0.0`、`@openuidev/lang-core@1.0.1`、`zod@3.25.76`；安装与锁文件更新使用 `--ignore-scripts`。

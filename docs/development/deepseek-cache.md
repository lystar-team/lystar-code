# DeepSeek 缓存优化

OpenAI 兼容请求在发送前按模型身份解析缓存默认值：官方 DeepSeek Provider、官方地址，以及 ID 或名称含 `deepseek`（忽略大小写）的第三方模型，默认启用 `supportsMidConvoSystemMessages`。该规则不依赖模型目录是否经过远端刷新；模型的显式 `true` 或 `false` 配置优先。自定义模型使用不含 DeepSeek 标识的别名时，可以显式配置该开关。

LYStar 已有的提示词更新机制会把变化的 section 追加为会话内 system 消息。启用该能力后，请求保留这些更新，不再把更新合并回最前面的提示词，避免因此重写已发送的消息前缀。若供应商不接受会话内 system 消息，应在该模型的 compat 中设置 `supportsMidConvoSystemMessages: false`。

DeepSeek 模型的 OpenAI 兼容、Anthropic Messages 和 Bedrock 请求按工具名称固定声明顺序，并递归固定 Schema 对象的字段顺序。数组顺序、描述、约束和工具真实变化保留；规范化只作用于请求副本。其他模型的声明顺序保持现有行为。

Anthropic Messages 的会话内 system 消息仍由供应商的显式兼容配置决定；Bedrock Converse 不支持这种消息格式，继续合并 system 消息。工具声明稳定化可独立生效。网关自身是否启用缓存、缓存路由和计费由供应商控制。

## 压缩摘要

压缩摘要请求重放对话在保留点之前的全部消息（包括提示词状态和上一次检查点），把压缩指令作为最后一条 user 消息追加。该请求因此成为上一次模型请求的前缀延伸，供应商可以复用已写入的缓存，而不是从系统提示词开始重新计算。这条路径不再把 `cacheRetention` 固定为 `none`，也不再隔离路由会话。

拆分轮次时只有历史摘要使用重放路径；轮次前缀摘要只覆盖保留点之前的同一轮消息，继续使用独立请求。分支摘要和 Bug Report 摘要不是请求前缀，也继续使用独立请求。头部缺失或加上生成预算后超过模型上下文窗口时，回退到摘要专用 system 提示词和拍平文本的原有路径，该路径会分块处理超长对话。

已用本机会话而非真实调用验证：在 6 个会话上，摘要请求体与同会话上一次请求的前缀逐字节一致、工具声明相同、指令位于末条 user 消息；头部超过上下文窗口时，请求与原来的独立路径完全相同。

重放头取自会话投影，并经过与正式请求相同的上下文转换链（隐藏声明、强制提示词和扩展 `context` 处理器）。依赖整段对话尾部的扩展处理器在头部切片上的输出可能与正式请求不同，此时只损失缓存复用，不影响摘要的正确性。

### 实测

2026-10-22 通过 `dmit-opencode` 网关的 `deepseek-flash` 调用真实压缩路径。每个会话先发送头部建立缓存（对应压缩前的那次正式请求），再依次执行新路径和旧路径。费用按官方 DeepSeek 单价对服务端返回的用量折算。

| 会话头部 | 旧路径（拍平，新前缀） | 新路径（重放头部） | 缓存读取占比 | 输入费用变化 |
|---|---:|---:|---:|---:|
| 38 条消息，含上一次检查点 | $0.003694 | $0.000213 | 97.38% | −94.2% |
| 30 条消息，拆分轮次，含上一次检查点 | $0.002843 | $0.000162 | 97.12% | −94.3% |

同一会话连续重放时，缓存读取占比为 97.12%、99.40%、99.85%，命中可重复。旧路径每次的拍平文本都不同，实际总是冷前缀；实测中它的缓存读取为 0。

风险是反向的：缓存不可用时，重放负载大于拍平负载。在同一会话首位插入哨兵使前缀失效后，新路径两次测得 $0.003362 和 $0.004654，比旧路径高 18% 和 26%；重放负载与拍平负载的比值取决于系统提示词大小，样本中最大为 6.6 倍。自动压缩紧跟在正式请求之后，前缀通常仍在缓存内；长时间空闲后的手动压缩可能遇到冷缓存。

样本只有两个会话、每条路径各一次有效调用，金额为按官方单价的估算，网关实际计费未核对。`estimateContextTokensUpperBound` 对同一头部给出的估算约为服务端计数的 4.3 倍（65,403 对 15,230）；它用于决定是否重放，偏保守只会退回拍平路径。

## 历史测量

以下记录来自 2026-10-22 的真实 DeepSeek API 调用。部分文件任务当时使用 DSH 工具执行，仅用于保留缓存测量依据，不代表当前版本仍内嵌 DSH，也不作为移除插件后的运行验收。

- [提示词更新对照](deepseek-cache/cache-comparison.json)：4 组对照；上下文更新后首次请求的 SDK 输入费用估算下降约 84.84%。
- [文件任务对照](deepseek-cache/cache-file-tasks.json)：3 组交错对照、6 个任务、25 次请求，结果均正确；更新后阶段输入费用合计下降约 66.95%，含预热及所有请求时下降约 26.81%。
- [场景补充对照](deepseek-cache/cache-scenarios.json)：10 项场景、28 次请求，覆盖文件任务、Workflow、分支、恢复和压缩；原行为与优化路径的缓存读取比例分别为 70.50% 与 81.41%。

缓存命中依据服务端 `usage.cacheRead`；费用按当次 SDK 模型价格估算。不同路径的请求数、输出与压缩内容存在差异，场景补充仅有一组顺序对照。上述样本不代表生产平均收益，也不能据此判断延迟改善。

以上记录均早于本文档描述的工具声明稳定化。工具声明稳定化只有本机请求体层面的验证，尚未取得真实供应商的对照；压缩摘要前缀复用已有上文的小样本实测。

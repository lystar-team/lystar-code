**截图与代码说明了什么**

截图中，同一个 service.ts 的分段读取占据数行。路径、行号、时间和展开按钮拥有相近的视觉权重，步骤目标与说明正文被穿插的工具记录割开。每条信息都有用途，但把它们放在相同层级会增加阅读负担。截图中央的截屏软件提示属于捕获异常，不纳入产品问题。

现有实现已有步骤、工具分组和完成后的「工作过程」折叠，不能把问题归因于缺少分组组件。运行中的主路径仍可逐项输出：conversation.tsx 的 renderToolStack 在 rows 模式下为每个工具渲染一次 ToolBatch；use-conversation-expansion.ts 对一个工具栈首次选择的呈现方式会保留在 Map 中；混合且未完成的 ToolBatch 也会渲染逐条 ToolBatchRow。单加折叠按钮或替换图标，仍会保留这种阅读结构。

| [Vercel Chain of Thought](https://elements.ai-sdk.dev/components/chain-of-thought) | 折叠的步骤结构支持搜索来源、图片与步骤状态 | 步骤关联证据、活动状态形成视觉锚点 | 展示已有步骤与公开活动；不把内部推理补为页面内容 |

| [Vercel Artifact](https://elements.ai-sdk.dev/components/artifact) | 生成内容可以有标题、内容区和操作入口 | 文件、图片、文档等结果获得独立预览 | 动作来自 LYStar 已有能力；不因官网有 Share、Regenerate 就加同名功能 |

这些组件提供呈现语汇；LYStar 的步骤关联、流式状态、原始记录与重连语义继续以项目实现为准。引入 AI SDK 的 useChat 不属于本方案。

**主视图怎样调整**

一次用户任务对应一段过程，关联正文、步骤与产物。步骤标题承担任务含义，活动摘要承担证据，当前状态提供查看执行记录的入口。完成步骤保留标题与结果摘要；当前步骤呈现最新活动。详细操作列表进入详情，正文保留连续阅读空间。

| 内容 | 主视图呈现 | 详情呈现 |
| --- | --- | --- |
| 读取文件 | 「已读取 N 个文件」与少量文件名入口；同一文件分段读取聚合为一个文件对象 | 原始调用顺序、完整路径、每次读取范围、输出与状态 |
| 搜索代码或网页 | 搜索目标、命中对象或来源摘要 | 搜索词、原始输出、来源链接与每次调用；查询仍执行中时保留状态 |
| 编辑、写入文件 | 文件名、操作类型，以及实际返回的 Diff 统计或差异预览 | 各次修改与 Diff；不把重复修改的行数相加当作净变更 |
| 运行命令 | 当前命令、执行状态与可查看的输出入口；结束后收为摘要 | 完整命令、终端输出、真实退出结果；只有已执行证据时使用「已执行」，不写「检查通过」 |
| 图片生成 | 生成中的稳定媒体框与完成后的图片预览 | 提示词、请求模型、查看大图与已有下载能力 |
| 智能体协作 | 成员身份、当前职责与真实状态；在步骤内形成成员组 | 对应子会话、发言和产物；成员增加时保留溢出入口 |
| 上下文压缩、Hook、Extension | 不影响任务的活动进入步骤摘要或记录入口 | 原始活动与状态；错误、等待输入等需要用户注意的情况在主视图保留摘要 |
| 最终结果 | 结论正文与实际产物入口 | 打开文件、Diff、图片或已有审阅视图；结果不埋进过程折叠区 |

示例：截图中的 service.ts 分段读取在主视图显示一个 service.ts 入口；点开后，每次行范围及其状态仍可检查。不同目录的同名文件不能被合并，聚合身份来自完整路径。读取次数与唯一文件数是不同计数，应给对应标签。

证据入口建议展示 2–4 个对象，其他对象进入「+N」入口。移动端限制为两行，完整路径进入详情。文件名需要消歧时显示短目录。卡片只承载有内容或操作的文件、图片、Diff 等对象；正文、时间与常规状态不用套卡片。

**运行、完成与异常**

| 状态 | 呈现规则 |
| --- | --- |
| 准备中、已排队 | 使用现有状态文案；当前对象尚未返回时保留真实缺口 |
| 运行中 | 当前步骤获得蓝色标记，显示最新活动；摘要内容更新，整个容器不反复入场 |
| 已完成 | 自动展开的成功过程可以收为摘要，用户主动打开的详情保留；最终正文与产物入口保持可见 |
| 出错 | 步骤主视图保留错误摘要及原因入口，关闭详情后也可发现；错误原文不改写成未经证实的原因 |
| 已取消、已中断 | 各自保留终态，记录可查看；不写成成功或统一写成失败 |
| 等待输入 | 当前问题与已有回复入口获得主视图空间，不能藏在工具分组内 |

一次工具出错不等于整项任务阻塞。展示状态必须来自现有数据，不用一次历史错误替整轮任务定性，也不因后续成功就删除该错误记录。

图中的三阶段轨道是结构示例。实现时，只有结构化计划或已收到的步骤能成为节点；缺少后续阶段数据时，只显示当前步骤与已有历史，不制造未来阶段、百分比或剩余时间。

**桌面与移动端的承载**

桌面建议使用紧凑项目栏、正文主区和按需审阅区。项目栏可考虑 280–320px 默认宽度，仍保留现有拖动范围；正文阅读宽度建议 760–880px。右侧详情复用审阅工作区，可承载本次选中的文件、Diff 或执行记录，不新增一块永久工具日志栏。总宽度不足以同时容纳正文与详情时，详情进入覆盖层。

| 视口 | 推荐呈现 |
| --- | --- |
| 390px | 单栏；项目与会话进入菜单；当前步骤摘要常见，历史步骤通过入口查看；短证据用底部抽屉，长代码、Diff、日志用全屏详情 |
| 768px | 正文主区；项目栏与详情进入覆盖层；保留当前对象上下文 |
| 1280px | 保留现有宽屏断点；正文、项目栏与审阅区能保留阅读宽度时并排，否则关闭一个次级区域 |
| 1440px 及以上 | 项目栏 + 正文 + 按需审阅区；正文与输入区对齐 |

移动端从底部抽屉进入全屏详情时，替换当前详情承载；不叠加第二层模态。关闭或返回后保留会话滚动位置、当前文件与输入草稿。代码可以在内容容器中横向滚动，页面本身不能横向溢出。

输入区保留输入、附件、当前模型与发送/停止；统计、思考强度等次级信息用现有菜单或可发现的展开入口承载。运行中继续保留调整方向和排队发送。移动端动作进入正常布局，命中区以现有 44px 要求为准；处理键盘与底部安全区。

协作工作区沿用相同正文与步骤语言：成员状态聚合为一组，点选成员查看子会话，看板仍是已有独立视图。有明确依赖数据和查看任务时才呈现关系图，普通过程不强制使用节点画布。

**保留配色，改变视觉节奏**

沿用 tokens.css 的背景、文字、品牌与状态色。浅色保持白底、浅灰表面与黑色正文，蓝色用于当前步骤、选中、链接和焦点。深色沿用 #151515 主底、#1e1e1e 高层表面与现有浅蓝品牌色。

步骤标题建议 16–18px，正文沿用现有 15px 量级，活动摘要约 13–14px，时间与路径等辅助信息约 12px。等宽字体留给路径、命令和代码；让任务标题与解释正文有不同字重和间距。分组使用细线与表面差，浮层和输入区才有阴影。动效使用既有能力，围绕展开、状态切换与进入详情，建议约 160–240ms；流式正文不逐段闪烁，减少动态偏好沿用现有处理。

**落地顺序与完成依据**

1. 先改运行过程的主视图：步骤容器、文件与检索聚合、运行时稳定摘要、错误可见性。确认一段多工具过程不再占据长列表。
2. 再统一结果与详情：文件、Diff、命令、图片、子会话使用各自内容；与已有审阅工作区、预览对话框关联，减少重复入口。
3. 完成移动端承载与壳层密度：短详情抽屉、长详情全屏、窄屏步骤摘要、输入区次级信息入口。

实现后需核对 390/768/1280/1440px、浅深主题、长路径、同名文件、七种工具状态，以及展开后继续流式更新、回看历史、切换会话、返回详情的行为。聚合前后记录数与原始状态应可对应；正文、产物和错误可达，输入、停止、调整方向与排队发送继续可用。

本轮只核对源码和生成图：未运行改版页面，未执行浏览器交互验收，也未验证图中抽屉和文件入口。概念图中的代码、阶段、计数与时间用于展示布局，不代表真实代码内容或执行结果。后续实现以项目组件、数据和实际视口为准；生成图片不能证明字体尺寸、触控命中区或响应式行为。
